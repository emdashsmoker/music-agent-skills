이 스킬은 신시사이저의 복화술사다. 스스로는 한 음도 소리 내지 않는다. 실제 LMMS 프로젝트를 쓰고, 창 없이 실행된 LMMS가 모든 소리를 낸다. 곡은 짧은 Python 스크립트로 쓴다. 내장 툴킷(`scripts/lmmskit`, 명령행 `scripts/lmms_tool.py`)이 스크립트를 프로젝트로 바꾸고, LMMS가 오디오를 렌더하고, 측정 도구가 화성, 편곡, 믹스, 가사 전달을 컴파일러가 코드를 검사하듯 점검한다. 기존 LMMS 프로젝트도 같은 도구로 열고, 분석하고, 고치고, 내보낸다.

결과물의 수준: 신시사이저 패치, 고전 드럼머신 사운드, 선택 사항인 합성 보컬로 만든, 구성이 갖춰지고 장르 어법에 맞는 완성 트랙이다. 잘 만든 시퀀서 작업물이나 탄탄한 데모 수준이다. 상업 스튜디오 마스터와 같지 않고, 합성 목소리는 사람 가수와 다르다. 기획 단계에서 이 점을 한 번 말해 사용자의 기대를 맞춘다.

## 원칙

- 에이전트는 들을 수 없다. 소리에 대한 모든 판단은 측정값이나 직접 열어 본 그림에 근거해야 한다. 스크립트만 보고 소리가 어떻다고 서술하지 않는다.
- 점검 결과는 컴파일 오류처럼 다루고, 취향은 사용자의 몫이다. `ERROR`와 `WARN`은 고치거나, 의도한 선택으로 사용자에게 보고한다. 사용자가 점검이 경고하는 선택(묻힌 보컬, 찌그러진 마스터, 거친 화음)을 고집하면 구체적 결과를 한 번 알린 뒤 사용자 뜻대로 하고 전달 노트에 기록한다.
- 같은 입력은 같은 출력을 낸다. 모든 무작위 선택은 고정 시드를 쓰고, `produce`는 두 번 렌더해 재현성을 증명한다. 곡 스크립트를 보관한다. 스크립트가 곡의 원본이며 이후 모든 변경은 스크립트를 거친다.
- 이 스킬의 수치(레벨, 범위, 임계값)는 관례와 측정으로 얻은 출발점이다. 곡과 사용자에 맞춰 조정한다. 참조 문서와 상황이 어긋나면 그 규칙이 무엇을 위한 것인지에서 출발해 판단한다.
- 사용자에게 비용이 드는 일은 먼저 묻는다. 사람이 쓰는 컴퓨터에 설치하는 일, 큰 다운로드, 긴 렌더, 보이스뱅크 이용 조건과 관련된 일, 부르게 될 가사가 해당한다.
- 사용자가 준 범위 안에 머문다. 샘플, 보이스뱅크, 타인의 자료를 스스로 찾아 가져오지 않는다.

## 새 환경에서 첫 곡을 만들기 전

`python scripts/lmms_tool.py doctor`를 실행한다. 아무것도 바꾸지 않고 이 컴퓨터에 무엇이 있는지 보고한다. 어떤 형태로든 설치된 LMMS(시스템 패키지, AppImage, Flatpak, 앱 번들), ffmpeg, Python 패키지, 그리고 일회성 컨테이너인지 사람이 쓰는 컴퓨터인지를 알려 준다. 이어서 `references/setup.md`를 읽고 컴퓨터의 성격에 맞게 행동한다.

- 일회성 컨테이너에서는 빠진 것을 설치하고 사후에 보고한다.
- 사람이 쓰는 컴퓨터에서는 무엇을 어떤 방법으로 설치할지 제안하고, 관리자 권한이 필요 없는 방법을 우선하고, 답을 기다린다. 이미 있는 LMMS를 쓴다. 관리자 권한 명령을 직접 실행하지 않으며, 사용자가 설치한 것을 바꾸거나 지우지 않는다.

`python scripts/lmms_tool.py selftest`는 1분 안에 설치가 제대로 동작하는지 증명한다. 첫 실행은 이 컴퓨터에 드럼 킷도 만든다(몇 초, LMMS 필요). 설정(특이한 위치의 LMMS, 캐시 폴더, 병렬 렌더 수 축소)은 환경 변수나 `lmms_tool.py configure`로 한다.

## 새 곡 만들기

단계를 순서대로 밟는다. 각 단계는 실패할 수 있는 확인으로 끝난다. 확인이 실패한 상태로 다음 단계에 가지 않는다.

### 1단계: 사용자와 기획

한 번의 질의로 기획을 모은다. 사용자가 이미 말한 항목은 건너뛰고, 짧은 답으로 충분하도록 대괄호 안에 기본값을 제시한다.

- 스타일이나 장르, 참고 아티스트나 곡(느낌의 참고용이며 멜로디나 가사는 베끼지 않는다)
- 분위기와 에너지
- 템포 [장르 프로파일의 기본값], 조성 [장르에 어울리는 단조]
- 길이와 형식 [노래 형식이나 클럽 형식으로 3-4분. 업리프팅 트랜스는 7-15분이며 기본 약 7분 30초]
- 보컬: 없음, 내장 TTS 목소리의 가창, 사용자가 제공하는 가수 보이스뱅크의 가창. `references/vocals.md`의 목소리 선택지를 제시한다. 언어 [영어]
- 보컬 점검용 인식 모델 [base]: 컴퓨터에 여유가 있으면(CPU 4코어 이상, 여유 메모리 2 GB 이상) small을 제안한다. 특히 다른 언어 가사는 base가 또렷하게 부른 줄도 약한 줄로 잡는 경우가 많다. medium 이상은 사용자가 원할 때만 쓴다. 선택은 `configure --set asr_model=<모델>`로 저장하며 모델별 비용은 `references/vocals.md`에 있다
- 가사: 사용자가 쓴 가사, 또는 사용자가 준 주제로 여기서 작성. 먼저 쓴 초안은 결함을 그대로 안고 가기 쉬우므로, 한 줄이라도 쓰기 전에 `references/vocals.md`의 가사 요령을 읽는다. 사용자가 쓴 가사도 목소리를 정한 뒤 같은 요령으로 검토해 고친 안을 제시하고, 사용자가 고른 대로 따른다
- 음색 선호 [장르의 통상 킷: 909, 808, 606, Linn, CR-78 계열 드럼, 303 계열 애시드 베이스 등]
- 믹스 스타일 [균형, 유연]: 전경(백비트, 리드, 리드 보컬)을 트랙의 어디에 둘지 하나. 균형은 백비트와 리드 보컬을 약간 앞에 두는 기본값이다. 전면은 팝이나 라디오 믹스로, 목소리와 백비트가 트랙 위에 선다. 보컬 전면은 목소리와 리드만 앞에 두고 백비트는 균형에 둔다. 백비트 전면은 그 반대다. 융합은 클럽 믹스로, 목소리와 리드가 트랙 속에 들어간다. 연주곡에는 보컬 전면을 빼고 제시한다. 전경은 백비트와 리드다. 준수는 유연과 고정 중 하나다. 유연이면 스타일은 출발점이고, 점검 결과에 따라 파트를 1-2 dB씩 옮기며 옮긴 것을 전달 노트에 적는다. 고정이면 전경 파트의 레벨과 더킹을 스타일 값에 두고 나머지로만 고친다. 선택은 스크립트의 `song.mix_style()`에 적고, 각 스타일이 레벨과 더킹과 판정 창을 얼마나 옮기는지와 준수의 규칙은 `references/mixing.md`의 믹스 스타일 절에 있다. 밝기는 톤 보정이 완성 음반 기준으로 맞추므로 어두운 믹스를 원할 때만 말한다
- 마스터 세기 [장르 목표, 깨끗한 리미팅]: 기본은 리미터가 가장 큰 순간을 3 dB까지만 깎는 깨끗한 마스터다. 핫 마스터는 장르 목표보다 1-2 LU 높이고 리미터 감쇄를 5 dB까지 허용하며, 펌핑과 뭉개진 킥을 받아들이는 선택이다(`references/mixing.md`의 음량 단계와 음량 목표 절). 스트리밍 서비스는 큰 마스터를 약 -14 LUFS로 낮추므로 큰 값은 밀도만 더한다
- 렌더 방식 [재현성 우선]: 이 항목은 반드시 묻고 선택지마다 비용을 말한다. 재현성 우선은 렌더할 때마다 같은 파일이 나오고 전체 믹스 렌더가 느리다. 속도 우선은 그 렌더가 빨리 끝나고 일부 곡은 렌더마다 조금 달라질 수 있다. 컴퓨터 여유 우선은 코어를 덜 써서 컴퓨터를 계속 쓸 수 있고 가장 긴 단계가 더 오래 걸린다. 표와 설정은 `references/setup.md`의 렌더 방식 절에 있다
- 전달물 [ogg, mp3, MIDI, LMMS 프로젝트, DAWproject 파일, 가사]
- 제목 [하나 제안]

`python scripts/lmms_tool.py genres <이름>`은 스타일의 프로파일을 출력하고, `references/genres.md`는 장르 어법을 설명한다. 프로파일이 없는 스타일은 장르 지식으로 기획하고 가정을 밝힌다.

그다음 기획을 몇 줄로 되돌려 쓴다. 제목, 장르, 템포, 조성, 마디 수가 붙은 섹션과 전체 길이, 섹션별 파트, 코드 진행, 보컬 방식, 믹스 스타일과 준수, 전달물을 담는다. 사용자의 확인이나 수정을 기다린다. 답할 사람이 없으면 기본값으로 진행하고 가정을 전달 노트 맨 위에 적는다.

요청이 불분명하거나 밝힌 목표에 비추어 의외이면 멈추고 묻는다. 분위기와 어긋나는 가사, 장르에서 크게 벗어난 템포, 형식이 채울 수 없는 길이가 그 예다. 어긋나 보이는 점을 말하고 구체적 대안 2개를 제시한다. 임의로 고쳐서 진행하지 않는다. 사용자가 원래 기획을 고수하면 예상되는 품질 저하를 한 번 명확히 고지한 뒤 기획대로 진행하고, 전달 노트에 해당 부분의 수치와 한계를 기록한다. 가사는 한 줄이라도 부르기 전에 전문을 보여 주고 승인을 받는다.

이 단계의 확인: 사용자가 기획을 확인했거나, 가정이 기록되어 있다.

### 2단계: 작곡

`references/composing.md`를 읽는다. 곡 스크립트를 쓴다. 섹션, 코드, 파트, 음표, 전환을 담는다. 실행한 뒤 다음을 돌린다.

```bash
python scripts/lmms_tool.py lint song.mmp
```

모든 `ERROR`와 `WARN`을 스크립트에서 고치고 다시 실행한다. 남기기로 한 항목은 말로 설명할 수 있는 이유가 있어야 한다. `section_density` 표를 읽고 기획한 에너지 곡선과 비교한다.

확인: lint에 설명되지 않은 경고가 없다.

### 3단계: 음색 선택과 다듬기

기본 패치가 맞지 않으면 `references/sounds-effects.md`를 읽는다. 후보를 오디션하고(`lmms_tool.py sounds a b c --out work/audition`) 표와 그림을 본 뒤 고른다. 주요 파트가 갖춰지면 가장 바쁜 섹션의 짧은 구간을 렌더한다(`render --bars`).

확인: 구간 측정에서 모든 파트가 들리는 수준이고, 무음이거나 레벨이 크게 어긋난 패치가 없다.

### 4단계: 보컬 (보컬이 있는 곡만)

먼저 `references/vocals.md`를 읽는다. 요약하면, 고른 목소리가 잘 부르는 단어와 문장 구조를 먼저 정하고, 가사 줄을 온전한 문장으로 쓰고 음절마다 멜로디 토큰 하나를 주고, 줄을 쓸 때마다 `lyric-lint`로 확인하고, 믹스 전에 보컬만 따로 불러 보고, 약한 줄에 단어 선택 절차를 적용하고, 드라이 보컬과 가사를 사용자에게 주어 승인을 받는다. `lyric-lint` 경고는 줄을 스크립트에 넣기 전에 정리한다. 스크립트를 저장하면 줄이 바로 불려지므로 먼저 잡은 결함은 비용이 들지 않는다. 프로젝트가 만들어진 뒤에는 `lint`가 모든 리드 줄에 같은 가사 검사를 되풀이한다.

가수 보이스뱅크를 쓸 때는 첫 렌더 전에 사용자와 이용 조건을 읽고 요구되는 크레딧을 표기한다. 가사 규칙 가운데 가창 요령과 모델 목소리의 습성만 보이스뱅크에 적용한다.

확인: 리드 보컬의 가사 줄을 사용자가 승인했거나, 경고가 붙은 줄을 인식기가 들은 내용, 음정 오차(센트), `ROUGH` 음절과 함께 목록으로 제시했다.

### 5단계: 믹스와 마스터

```bash
python scripts/lmms_tool.py produce song.mmp -o out
```

측정으로 파트 레벨의 밸런스를 잡고, 장르에 맞는 마스터 음량을 정하고, 렌더하고, 모든 점검을 돌리고, 그림을 그리고, 모든 내보내기 파일을 쓴다. 몇 분 넘게 걸릴 때는 사용자에게 먼저 알린다(소요 시간은 `references/mixing.md` 참조).

확인: `produce`가 끝났고 `out/report.txt`가 있다.

### 6단계: 검수

`references/visual-qa.md`를 읽고 검수 순서를 밟는다. `report.txt`를 읽고 모든 그림을 본다. 이미지를 실제로 연다. 그림이 보여 주는 것을 기획과 비교한다. 문제마다 `references/mixing.md`에서 원인을 찾고, 스크립트를 고치고(EQ보다 편곡과 레벨이 먼저), 5단계를 다시 돌린다.

리포트가 깨끗하거나 남은 항목이 의도한 것일 때 반복을 멈춘다. 같은 경고 3개 이상이 두 번의 수정 뒤에도 남으면 멈추고 그림과 함께 사용자에게 보여 준다.

확인: 모든 그림을 열어 보았고, 남은 `WARN`마다 이유를 밝혔다.

### 7단계: 전달

짧은 노트와 함께 넘긴다.

- 오디오: `.ogg`와 `.mp3`(요청 시 `.wav`)
- `.mid`, `.mmp` 프로젝트, `.dawproject`, `.project.json`. 다른 컴퓨터의 LMMS에서 쓸 때는 `lmms_tool.py pack song.mmp -o song.zip`
- 보컬 곡은 가사 파일과 드라이 리드 보컬
- 개요 그림
- 사용자가 나중에 수정을 원할 수 있으면 곡 스크립트

노트에는 제목, 장르, 템포, 조성, 길이, 음량, 믹스 스타일과 준수(유연이면 스타일에서 옮긴 파트와 양), 사용한 렌더 방식을 적는다. 무엇을 점검했고 그림이 무엇을 보여 주었는지, 남은 경고와 남긴 이유, 세운 가정, 적용되는 크레딧과 이용 조건(목소리, 보이스뱅크), 합성 음성이나 보이스뱅크로 부른 파트가 어느 것인지도 적는다. 사용자가 만족 여부를 판단하는 데 필요한 내용만 담는다.

## 기존 LMMS 프로젝트 작업

`references/lmms-projects.md`를 읽는다. 요약은 다음과 같다.

1. 파일을 복사해 사본에서 작업한다. `inspect`, `lint`, `check`(렌더, 측정, 그림) 순으로 본다.
2. 적용되는 한계를 먼저 사용자에게 알린다. 누락된 샘플, VST나 SoundFont 의존성, 매우 큰 프로젝트, 렌더할 때마다 달라지는 음원이 해당한다.
3. 점검 결과를 마디 번호와 함께 음악 용어로 보고하고, 측정된 결함, 관례에서 벗어난 점, 취향의 제안으로 나눈다.
4. 사용자가 요청한 수정만 하고, 변경마다 목록에 적고, 렌더하고, 점검하고, 전후를 비교한다.
5. 필요한 형식으로 내보낸다.

## 완성된 곡 고치기

곡 스크립트를 고치고 변경 지점 이후의 단계를 다시 돌린다. 보컬 줄은 캐시되므로 바뀐 줄만 다시 부른다. 스크립트가 있는 곡은 렌더된 오디오를 덧대거나 생성된 프로젝트를 손으로 고치지 않는다. 다음 실행에서 변경이 사라지기 때문이다.

## 참조 문서

각 문서에는 해당 단계에 필요하지만 이 파일이 되풀이하지 않는 내용이 있다. 작업이 익숙해 보여도 단계에 들어가기 전에 문서를 읽는다.

| 문서 | 읽는 시점 |
|---|---|
| `references/setup.md` | 새 환경의 첫 실행, LMMS나 패키지 누락, 렌더 실패, 무엇이든 설치하거나 설정할 때 |
| `references/composing.md` | 곡 스크립트를 쓰거나 고칠 때. API, 표기법, 편곡 요령, lint 점검 결과 |
| `references/genres.md` | 모든 트랙의 기획. 스타일별 템포, 드럼 그리드, 베이스, 화성, 음색, 형식 |
| `references/sounds-effects.md` | 음색 선택과 설계, 이펙트 추가, 오토메이션, 재현성 규칙 |
| `references/vocals.md` | 모든 보컬. 목소리, 보이스뱅크와 이용 조건, 가사 쓰기, 단어 선택, 줄 끝 처리, 보컬 믹스 |
| `references/mixing.md` | `produce` 실행, 리포트 읽기, 점검 결과별 조치 |
| `references/visual-qa.md` | 그림으로 렌더 결과를 검수할 때 |
| `references/lmms-projects.md` | 곡 스크립트에서 나오지 않은 프로젝트를 열고, 분석하고, 고치고, 내보낼 때. 모든 내보내기 형식 |

## 예제 곡

`examples/`에는 완성곡 4개가 스크립트로 들어 있고 MIDI 파일과 가사가 함께 있다. 업리프팅 트랜스 연주곡, 애시드 테크노 연주곡, 가창이 있고 드럼 편곡이 2가지인 퓨처팝 곡, 낮은 보컬의 두머 곡이다. 새 스크립트를 쓰기 전에 과제와 가장 가까운 예제를 읽는다. 섹션 설계, 에너지 곡선, 보컬 줄, 믹스 조작이 동작하는 형태로 들어 있다. `examples/README.md`에 예제별 시연 내용과 실행 방법이 있다. 예제는 현재 폴더에 프로젝트를 쓰므로 작업 폴더에서 실행한다.

## 명령

`python scripts/lmms_tool.py <명령> -h`가 모든 명령을 설명한다: `doctor`, `configure`, `kit`, `selftest`, `genres`, `sounds`, `inspect`, `lint`, `render`, `balance`, `master`, `check`, `produce`, `export`, `import-json`, `pack`, `voices`, `sing`, `compare`, `lyric-lint`.

도구가 출력하는 메시지와 리포트는 영어다. 사용자에게 전할 때는 사용자의 언어로 옮긴다.
